## Part A — Remove the dead yaml dependency + fix the stale UI string (#321)

**A1. Drop `gopkg.in/yaml.v3`.** It is a *direct* require at `parts_master_go/go.mod:12` with
**no `.go` importer** (the yaml load block was removed in #313). Remove it with tidy, not a
manual edit (tidy also fixes `go.sum`):
```bat
cd parts_master_go
go mod tidy
```
Confirm `gopkg.in/yaml.v3` is gone from both `parts_master_go/go.mod` and `go.sum`. If
`go.work.sum` at the repo root changed, that is expected — include it in the commit.

**A2. Fix the stale Settings-page text.** PO defaults are persisted to
`config/local.pm.json` (via `SaveLocal`), not a yaml file. In
`parts_master_go/templates/settings.html:143` replace:
```html
            Overrides <code>config/settings.yml</code>. Connect to the database to see contact names.
```
with:
```html
            Saved to <code>config/local.pm.json</code>. Connect to the database to see contact names.
```

## Part B — Collapse the vestigial `Settings` wrapper into `Config` (#321)

`config.Settings` now wraps a single field (`PODefaults`). Flatten it so callers read
`cfg.PODefaults.*` instead of `cfg.Settings.PODefaults.*`. Mechanical; no behavior change.
Only **8 call sites across 3 files** (plus the struct definition) — verified by grep.

**B1. Edit the struct in `parts_master_go/config/config.go`.** Change the `Config` field
(line ~25) and rename the wrapper type (lines ~28–33):
```go
// in type Config struct {...}
	TestRecordsURL    string
	PODefaults        PODefaults   // was: Settings Settings
}

// replaces type Settings struct { PODefaults struct {...} }
type PODefaults struct {
	ContactID  int
	ReceiverID int
}
```
Then update the two assignments inside `Load()` (lines ~96, ~99):
`cfg.Settings.PODefaults.ContactID` → `cfg.PODefaults.ContactID`, and likewise `ReceiverID`.

**B2. Update the remaining 6 call sites** (simple find/replace of
`cfg.Settings.PODefaults` → `cfg.PODefaults`):
- `parts_master_go/handlers/pos.go:243,251` — `h.cfg.Settings.PODefaults.ContactID` /
  `.ReceiverID`.
- `parts_master_go/handlers/settings.go:78,79,149,150` — two reads (template data map) and
  two writes.

The compiler will catch any missed site (`cfg.Settings` will no longer exist), so a clean
build is full verification for this part.

## Part C — Secret-scan audit (audit half of #227 only)

Goal: confirm no secrets (DB passwords, `SESSION_SECRET` values, full DSNs) are present in
the git history, and **report findings in the PR description**. Do **not** make the repo
public — that decision stays with the user.

**C1. Confirm the sensitive files were never tracked:**
```bat
git log --all --full-history --oneline -- .env "config/local.pm.json" "config/local.tr.json" "**/config/local.*.json"
```
Expect **no commits**. Any output means a secrets-bearing file was committed at some point —
record the commit(s).

**C2. Grep history for secret patterns** (real values, not placeholders like `change-me`):
```bat
git log -p --all -S "DB_PASSWORD"
git log -p --all -S "SESSION_SECRET"
git log -p --all -S "sqlserver://"
```
Treat hits in `.env.example`, docs, or with placeholder values as clean. If history is
large, sampling the patterns above is sufficient.

**C3. Report.** Summarize the result (clean / specific findings) and post it as a comment on
#227. Because the "unprivate repo" half is the user's call, **leave #227 open** with the
audit comment, unless the user says to close it.

> If C1/C2 reveal a real committed secret, **stop and surface it to the user** — purging git
> history is a separate, destructive operation (filter-repo / force-push) that needs explicit
> sign-off. Do not rewrite history under this plan.
