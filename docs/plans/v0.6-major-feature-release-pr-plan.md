## Which PRs require a DB update on upgrade

`SQL/*.sql` files are **reference DDL, not migration runners** — they are not executed
automatically. So any PR that changes the schema (new table, new column, or a trigger
change) requires the admin to **manually run the DDL against the production DB *and* the
`ArxDev` test DB** before/after dropping in the new `Arx.exe`. PRs with no schema change
are pure binary swaps.

These are design-level estimates — the issues aren't built yet, so a few depend on final
approach (flagged ⚠️).

## Backward compatibility with 0.5.12

"Non-backward-compatible" here means: **after this PR's DB migration is applied, can the
old 0.5.12 `Arx.exe` still run against that database?** This matters for rollback safety
and any window where the old binary might still point at the migrated DB.

Verified fact that shapes this: the app's read queries use **explicit column lists** and
explicit positional `Scan` (not `SELECT *` into a flexible map). So adding a column does
**not** break the old binary's reads — it only selects the columns it knows about.

### Backward-compatible (old 0.5.12 keeps working)

- **All new-table PRs** — ~~#274~~ ✓, #289, #251.
  The 0.5.12 binary never references the new tables, so it ignores them.
- **New-column PRs *if* the columns are nullable or have a DB default** — #271, #267, ~~#270~~ ✓,
  ~~#272~~ ✓, #269, #249/#250, #256/#257, #260. Old binary omits them on INSERT and the DB fills
  the default; old reads don't select them.

### Non-backward-compatible (old 0.5.12 breaks or degrades)

| PR | Issue | Why |
|---|---|---|
| TR row archive/retire | #403 | Replaces the HIDE workaround. If the migration removes/repurposes HIDE, 0.5.12 (which filters on it) shows retired rows or errors. |
| Any new-column PR done with **NOT NULL and no default** | — | 0.5.12 INSERTs omit the column → writes fail. Avoidable: make new columns nullable or defaulted. |

### Degraded but not broken (audit data only)

- ~~**F1 — user identity** (#207)~~: shipped. Trigger changes are live; rollback to 0.5.12 would record `SYSTEM_USER` instead of the app user — correctness regression, not a crash.
- ~~**Definition history** (#389)~~: shipped. Rollback to 0.5.12 resumes capturing only changed rows (old behavior), not prior values.

### Takeaway

Most of v0.6 can be made rollback-safe by following two rules: **add, never alter** (new
tables and additive columns), and **make every new column nullable or defaulted**. The only
inherently incompatible change is the restructure in #403 (HIDE removal).
