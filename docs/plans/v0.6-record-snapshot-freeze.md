# Plan — Freeze saved test records to their snapshot (#487)

## Problem

A saved test record is supposed to be a frozen snapshot of the definition as it was
when the record was taken. Today it is only **partially** frozen:

- `test_result` snapshots `parameter, specification, spec_min, spec_nom, spec_max, spec_units`
  on **first INSERT only** (`SaveResults`, records.go ~1822).
- Reads (`RecordDetail` / `RecordPrint` / `EditRecord`) only select `parameter, specification`
  back; the persisted `spec_*` snapshot columns are **never read**. Everything else
  (spec limits, units, `pf_type`, `format`, `default_result`, `hide_formula`) is pulled
  from the **live** `test_definition`.
- Stored `parameter` / `specification` are **raw** (tokens like `{15}`, `{nom}` unresolved),
  while the live-fallback render path resolves them — inconsistent rendering.
- The UPDATE path never refreshes snapshot columns, and `ComputePassFail` on re-save
  evaluates against **live** limits, so P/F can silently drift.

Net effect: editing a definition changes what old records display. Issue #487 wants the
opposite — "old records should never show the latest of anything" — plus an explicit
**"update this record to the latest form"** action that re-snapshots on demand.

## Decisions (confirmed)

1. **Full freeze.** Saved records render entirely from their own snapshot.
2. **Store resolved values.** Tokens are substituted at save time; the snapshot is self-contained.
3. **Full re-sync action.** An explicit button on an unlocked record re-pulls the current
   definition into the snapshot (refresh existing rows, add new steps, drop archived-with-no-result,
   recompute P/F against the new limits).
4. **No backfill migration.** Existing records already carry most snapshot data; missing values
   are display columns. Where a snapshot field is empty, fall back to the live definition (status quo).
5. **`default_result` is NOT snapshotted.** On a saved record the Result column already holds the
   entered value; the live default never legitimately applies. Drop it from the snapshot set and
   from the `EffectiveValue` fallback for saved rows.

## Snapshot column set

`test_result` already has: `parameter, specification, spec_units, spec_min, spec_nom, spec_max`.

**Add two columns:** `pf_type VARCHAR(255)`, `format VARCHAR(255)`.

(`pf_type` is needed to recompute P/F against frozen limits on edit; `format` is needed so the
result value renders as it did when recorded. `default_result` / `hide_formula` are intentionally
not snapshotted.)

## Changes

### 1. Schema (additive, rollback-safe) — the column-add discipline

- **`SQL/TestRecords.sql`** — add `pf_type VARCHAR(255)` and `format VARCHAR(255)` to the
  `test_result` DDL (after `spec_max` / before `updated_at`).
- **`SQL/migrations/migrate_record_snapshot.sql`** (new) — idempotent `IF COL_LENGTH(...) IS NULL`
  guards adding each column (same shape as `migrate_tr_archive.sql`).
- **`SQL/_test.sql`** — likely **no change**: both new columns are nullable with no default, so
  `SELECT * INTO ArxDev` copies them cleanly (no DEFAULT constraint to re-add). Verify and only
  touch if the populate script enumerates columns explicitly.
- **`SQL/schema.md`** — update the `test_result` table reference to list `pf_type` and `format`
  as snapshot columns; note that saved records render from these, not the live definition.

### 2. Model — `arx_go/models/trmodels.go`

- Add `PFType string` and `Format string` to `TestResult` (snapshot fields).
- Update `EffectiveValue()` so that **for a row backed by a result** it returns the stored result
  and does **not** fall back to `Step.DefaultResult` (decision 5). The default fallback should only
  apply to rows with no result (new/unrecorded steps in the edit view).
  - Simplest: leave `EffectiveValue` as-is but make the snapshot-hydration (below) set
    `Step.DefaultResult = ""` for hydrated rows, so the fallback is a no-op. Choose whichever is
    cleaner; prefer not changing the method signature.

### 3. Render path — hydrate `Step` from the snapshot (`arx_go/records.go`)

The cleanest, most surgical approach: keep loading live steps as today, but **when a result snapshot
exists, overwrite the render-relevant `Step` fields from the snapshot** before building each
`ResultRow`. Then every existing template binding (`.Step.SpecMin`, `.Step.PFType`, `.Step.Format`,
`.EffectiveSpec`, `.EffectiveParameter`, `.EffectiveValue`) automatically reflects the frozen values
with no template changes.

Add a helper, e.g.:

```go
// hydrateStepFromSnapshot copies frozen snapshot fields from a recorded result onto the
// step used for rendering, so a saved record shows what it was taken under, not the live def.
// Only fields that are non-empty in the snapshot override the live value (decision 4 fallback).
func hydrateStepFromSnapshot(step *models.TestStep, res *models.TestResult) {
    if res == nil {
        return
    }
    if res.Parameter != "" { step.Parameter = res.Parameter }
    if res.Specification != "" { step.Specification = res.Specification }
    if res.SpecMin != "" { step.SpecMin = res.SpecMin }
    if res.SpecNom != "" { step.SpecNom = res.SpecNom }
    if res.SpecMax != "" { step.SpecMax = res.SpecMax }
    if res.SpecUnits != "" { step.SpecUnits = res.SpecUnits }
    if res.PFType != "" { step.PFType = res.PFType }
    if res.Format != "" { step.Format = res.Format }
    // default_result deliberately not snapshotted; clear so EffectiveValue won't show a live default.
    step.DefaultResult = ""
}
```

Apply in **`RecordDetail`** and **`RecordPrint`**:
- Add `pf_type, format, spec_min, spec_nom, spec_max, spec_units` to the `test_result` SELECT and scan
  them into the new `TestResult` fields.
- Because the snapshot is already resolved (decision 2), **skip `substituteRefs`/`substituteStepSelf`
  for rows that have a result** — those tokens are baked in. Only resolve for result-less rows.
  (Important: the current unconditional `substituteRefs` loop would re-resolve a baked string; since
  resolved snapshots have no tokens it's a harmless no-op, but the guard avoids re-resolving against
  live cross-step results.)
- After building each `ResultRow`, call `hydrateStepFromSnapshot(step, results[tid])`.

Apply in **`EditRecord`** (and the matching `SaveResults` load):
- Add the same columns to the slim `test_result` SELECT/scan.
- Hydrate `Step` from the snapshot so the editor's `data-spec-min/max`, `data-pf-type`, and `{{.Step.Format}}`
  reflect the frozen spec. Editing a recorded value then re-evaluates against the snapshot, not live.
- Rows with **no** result (newly added steps not yet recorded) keep live values so the user can record them.

### 4. Save path — store resolved snapshots (`SaveResults`, records.go)

- **INSERT** (`result != "" || comment != ""`, currently ~1822): before storing, resolve tokens the same
  way the render path does, then store the resolved strings into `parameter, specification`, and store
  the (already literal) `spec_min, spec_nom, spec_max, spec_units, pf_type, format`. Resolution needs the
  full results map, so do it in a **second pass**: write all raw result values first, then reload the
  record's results and, for each newly-inserted row, compute resolved `parameter`/`specification`
  (via `substituteRefs` + `substituteStepSelf`) and `UPDATE` the snapshot columns.
  - If a simpler one-pass is acceptable for the common case (no cross-step `{id}` tokens), resolve with
    the in-batch values available; but the second-pass approach is correct for cross-references.
- **P/F on INSERT and UPDATE**: compute `ComputePassFail` against the **snapshot** step (which on INSERT
  equals live). On UPDATE, build a transient `TestStep` from the existing snapshot columns (read in the
  existing-results query) so re-saving a value evaluates against the frozen limits. Do **not** modify the
  snapshot definition columns on UPDATE.

### 5. New action — "Update to latest" / re-sync

- **Handler** `ResyncRecord` — `POST /records/{id}/resync` (mirror `ArchiveStep`'s tx + `SET CONTEXT_INFO`
  pattern if a history trigger applies to `test_result`; otherwise a plain tx).
  - Reject if the record is locked (redirect to the record like the edit guard).
  - Load live steps (resolved against this record's results/context), then for the record's result rows:
    - **Existing results**: overwrite `parameter, specification, spec_min, spec_nom, spec_max, spec_units,
      pf_type, format` with the current resolved definition values, and recompute `pass_fail` against the
      new limits.
    - **Newly-added steps** that now apply (instrument-type filter, not archived, not hidden): no result
      row is created (no recorded value yet) — they will simply appear on the next edit. Do **not** fabricate
      empty results.
    - **Archived steps with an existing result**: leave the result (decision: don't delete data); it stays
      visible per `stepVisibleOnRecord`. Archived steps with no result already don't appear.
  - Also refresh `test_record.test_order` from the form's current `test_order` so newly added steps slot in.
  - Redirect back to `/records/{id}` with the refreshed snapshot.
- **Route**: register in `arx_go/main.go` next to the other `/records/{id}/...` POST routes.
- **UI**: add an "Update to latest" button on `records_show.html` next to Edit/Lock/Print, wrapped in a
  confirm dialog (it overwrites the frozen snapshot and re-evaluates P/F). Guard with `{{if not .Record.Locked}}`.
  Use `class="btn btn-sm btn-outline-secondary"` and a Bootstrap icon (`bi-arrow-repeat`).

### 6. Tests

- Unit-test `hydrateStepFromSnapshot`: snapshot values override live; empty snapshot fields fall back to live;
  `DefaultResult` is cleared.
- Unit-test the P/F-against-snapshot path if it's factored into a pure helper (build a `TestStep` from
  snapshot columns → `ComputePassFail`).
- Integration test (`//go:build integration`, ArxDev only) is the right place to assert the end-to-end
  freeze: save a record, edit the definition limit, reload the record → shows the old limit; run resync →
  shows the new limit and recomputed P/F. Offer this; don't add unless wanted.

## Out of scope / watch-outs

- The **edit** view intentionally evaluates the value the user is typing. Under full freeze it must evaluate
  against the **snapshot**, not live — this is the whole point. Make sure the `data-spec-*`/`data-pf-type`
  attributes come from the hydrated (snapshot) step, and that the client-side P/F JS therefore matches what
  `SaveResults` will store.
- Resolved-snapshot storage means a record taken before this change still has **raw** stored
  parameter/specification. The render guard ("skip resolve when a result exists") would then show raw tokens
  for those old rows. Mitigation: only skip resolution when the stored value contains no `{` token, else
  resolve as today. This keeps old raw snapshots rendering correctly while new resolved ones are used verbatim.
- Keep all changes behind `cfg.*Table()` helpers; no hardcoded table names.
- One CHANGELOG entry (`closes #487`), milestone `v0.6 Major Feature Release`.

## Addendum — confirmed materialization model (supersedes the partial-snapshot approach above)

Decision (confirmed): a saved record is a **fully materialized, self-contained snapshot**. Edit is
always against the frozen snapshot; "Update to latest" is the only path that re-pulls the live
definition. New records are frozen **from creation**. Section headings are frozen too. We do NOT use
definition-history reconstruction (the AFTER-UPDATE-only trigger can't rebuild as-of state, and it
would split each record across two temporal models).

### Schema — `test_result` mirrors the renderable definition

Beyond `pf_type`, `format` (already added), add:
- `type INT NOT NULL DEFAULT 0` — so headings (type > 0) live in `test_result` and render without the
  live definition. DEFAULT 0 backfills existing rows as data rows (they are all data rows today).
- `hide_formula VARCHAR(255)` — frozen visibility; evaluated at render against the record's **own**
  results, so a later hide-formula edit never changes an old record.
- `default_result VARCHAR(255)` — re-included (reverses the earlier "drop it" call). On a record
  materialized at creation every result starts empty, so the edit page needs the frozen default
  formula for auto-calc/pre-fill. Never shown on the read-only view.

`instrument_types` is NOT snapshotted: instrument filtering is baked at creation (the record's
instrument type is fixed, so only applicable steps are materialized). Archived steps are not
materialized onto new records.

### Token resolution split (confirmed)

- **Baked at creation:** self tokens (`{nom}/{min}/{max}/{units}`), `{record.*}`, `{form.*}`.
  Implementation trick: `substituteRefs(s, nil, nil, &record, &form)` leaves numeric `{id}` tokens
  intact (nil results/steps) while resolving record/form tokens; `substituteStepSelf` bakes self tokens.
- **Resolved at render:** `{id}` cross-step tokens, against the record's **own** materialized results
  (build a synthetic steps map from the result rows for the spec_nom fallback). Still frozen — never
  touches the live definition.

### CreateRecord — materialize

After inserting `test_record`, for each step in the form's `test_order`:
- skip archived steps and steps whose `instrument_types` don't apply to this record's instrument type;
- resolve baked tokens (above); insert a `test_result` row carrying `type`, `parameter`,
  `specification`, `spec_min/nom/max/units`, `pf_type`, `format`, `hide_formula`, `default_result`,
  with empty `result/comment/pass_fail`.

### Read paths (RecordDetail / RecordPrint / EditRecord)

Iterate `record.OrderedTestIDs()`. For each id:
- if a materialized `test_result` row exists → build the `TestStep` from the snapshot (incl. `Type`),
  evaluate frozen `hide_formula` against the record's own results, resolve `{id}` tokens, render;
- else (legacy/un-materialized row on a pre-#487 record) → fall back to the live `test_definition`
  exactly as today. This keeps old records (no heading/empty rows materialized) from losing rows until
  "Update to latest" backfills them.

So live steps are still loaded, but only as a fallback; new records never use it.

### SaveResults — no re-snapshot

Only writes `result/comment/pass_fail`, computing P/F against the row's frozen `spec_min/max/pf_type`.
Never rewrites the snapshot definition columns. (Rows always exist now — materialized at creation.)

### ResyncRecord — reconcile

Extend the existing handler: update existing rows from the current resolved definition; INSERT rows for
newly-added/applicable steps; refresh `type` and the record's `test_order`; recompute P/F. Leave rows
for removed/archived steps that already hold a result. This is the only re-pull path.

### Watch-outs

- `TestReport` and any aggregate over `test_result` must filter `result <> ''` now that empty rows exist.
- Heading rows now have a non-nil `Result` (empty) — template heading branches key on `Level`/`Type`, so
  fine, but audit any `if .Result` checks.
- Backfill: existing records render headings/unrecorded rows via the live fallback until "Update to
  latest" is run on them (or a one-time materialize migration — optional, user said most data exists).
